# Buy or Wait? — HackerRank Orchestrate

This repository implements a deterministic financial decision agent for the HackerRank challenge: for every request in `dataset/requests.csv`, decide whether the user should pay in full, pay partially, use installments, wait, or avoid the purchase.

The project is written in Python and is designed to be deterministic, explainable, and validation-friendly. It reads the challenge datasets, reconstructs the user’s cash flow, simulates a 90-day safety window, evaluates eligible payment methods, and writes a final `output.csv` in the exact schema required by the prompt.

---

## Challenge objective

The system must answer each request using the user profile, recent financial events, payment options, messages, and image-derived evidence when relevant. The final recommendation must:

- keep the balance above the user’s `minimum_balance_to_keep`
- cover recurring and essential expenses
- respect protected spending categories and payment preferences
- honor valid installment schedules from `request_payment_options.csv`
- produce a single valid row per request in the required output format

A full description of the rules is in `problem_statement.md` and `AGENTS.md`.

## Setup

### Prerequisites

- Python 3.10+
- `pip` available on PATH
- Optional OCR support: Tesseract and Pillow if you want image-based amount extraction to work for blank event amounts

### Install dependencies

```bash
python -m venv .venv
# Windows
.venv\Scripts\activate
# macOS/Linux
source .venv/bin/activate

pip install pandas pillow pytesseract
```

> Tesseract itself is a system dependency. If OCR is unavailable, the project still reads all structured CSV data and continues without image parsing.

### Run the agent

From the repository root:

```bash
python code/main.py
```

This writes the final predictions to the root-level `output.csv`.

### Validate output

```bash
python code/evaluation/main.py
```

This script checks the generated output against the challenge contract and prints a row count plus any schema or logical errors.

## Approach overview

The solver is intentionally rule-based and deterministic rather than relying on an LLM to decide in free-form logic.

### 1. Load and normalize input data

The agent reads all challenge CSVs from `dataset/` and loads:

- the user profile
- transaction history and pending events
- payment options per request
- exchange rates
- supporting messages and image metadata

It normalizes dates, cleans amounts, and collapses linked event lifecycles so that `pending`, `settled`, `cancelled`, and `failed` records are not double-counted.

### 2. Reconstruct a user cash flow

The system creates a 90-day forecast using:

- confirmed recurring income
- confirmed recurring expenses
- scheduled debits and credits
- essential spending categories
- minimum balance rules
- payment-option schedules

It also filters out pending credits, failed/cancelled transactions, duplicate lifecycle records, and unrealized investment values.

### 3. Compute safe payment capacity

For each request, the solver calculates:

- the maximum safe amount payable on `request_date`
- the earliest date when the full requested amount can be paid safely
- whether flexible recurring spending changes are required to make the payment feasible

This is done by evaluating the projected balance against the user’s `minimum_balance_to_keep` across the forecast period.

### 4. Rank eligible payment methods

The system evaluates candidate plans for:

- `full_payment`
- `wait`
- `installments`
- `partial_payment`
- `not_recommended`

When multiple safe plans exist, it prioritizes the option that:

1. completes the request by the deadline
2. avoids spending changes
3. minimizes total payment cost
4. starts earlier
5. uses fewer payments
6. falls back to the lowest payment option ID for ties

### 5. Validate and emit the final output

Before writing predictions, the agent enforces rules such as:

- valid amount bounds
- exact output column order
- allowed affordability statuses and payment methods
- valid payment-plan formatting
- installment plan matching a supplied option
- safe minimum-balance constraints

## Output contract

The final file must contain these columns in order:

```text
request_id,amount_safe_to_pay,affordability_status,recommended_payment_method,payment_plan,earliest_date_for_full_payment,spending_changes_needed,decision_explanation
```

The solver writes exactly one row for each request in `dataset/requests.csv`.

Key rules:

- `amount_safe_to_pay` is between `0` and the requested amount
- `affordability_status` is one of:
  - `affordable_now`
  - `affordable_with_plan`
  - `affordable_later`
  - `not_affordable`
- `recommended_payment_method` is one of:
  - `full_payment`
  - `partial_payment`
  - `installments`
  - `wait`
  - `not_recommended`

## Submission guidance

The final submission expects:

- `output.csv` at the repo root
- a runnable solution bundle in `code.zip`
- the required `evaluation/usage_report.md` inside the zip for token/cost tracking
- the `log.txt` transcript as the chat transcript, if required

Before submission, confirm that:

- all request IDs are present exactly once
- every payment method and affordability status is valid
- each payment plan is chronologically ordered and consistent with the recommendation
- the output file is produced from the challenge datasets only
